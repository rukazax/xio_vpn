## Детали по проверкам

### 1. Подготовка (сервер и импорт профиля)

Дерево приложения: `app/lib/subclients.dart` (`provisioningBundle`, строки 130–260) —
именно этим кодом приложение собирает дочерний профиль. Я повторил его на бридже
(`provision.py`, `provision3.py`, `add_awg_static.py`): X25519-ключи через `wg genkey/pubkey`,
`secret`/`entryToken` — по 32 случайных байта, дальше `admin.py` через stdin.

**Дефект D4.** `add` на развёрнутом сервере падает:

```
UnboundLocalError: cannot access local variable 'public' where it is not associated with a value
  File "/usr/local/lib/xio-managed/admin.py", line 606, in dispatch
    return {'user':dict(id=uid,…),'server':public(d),'configs':configs}
```

Причина — затенение имени: в ветке `add-awg` локальная переменная `public=req['publicKey']`
делает `public` локальной для всей функции. В репозитории (HEAD `4385d4a`,
`server/managed/admin.py`) это **уже исправлено** (`public_key=req['publicKey']` с комментарием),
но на бридже лежит старая версия (`md5 6cbee3e019a654de0e08f809d5a4097d`, `grep public_key` = 0).

Побочный эффект важнее самой ошибки: пользователь, его RIVET-креды и stack-профили
**уже закоммичены**, когда исключение вылетает на `return`. То есть провижининг не атомарен:
API отвечает «Server operation failed», а пир на сервере живёт. Ключи я сохранял до вызова,
поэтому пользователь `e38cfe89…` (slot 6) и его bundle (2612 Б: `awg`+`rivet-h3`+`rivet-s1`+`xray`)
восстановлены из `deployment.json` без повторного создания.

Статический AWG (`add-awg`, slot 5, `7a1c9e04…`, pubkey `mnFWbOHI/FMvrzB86Cmyh699ad+ySSokaqtEpPNWzCY=`)
отработал штатно и дал `.conf` 386 Б; для проверки 5 я импортировал вариант с `DNS = 9.9.9.9`.

Импорт в приложение: `xio://`-бандл и `.conf` принимаются пунктом
«Соединение → Файл с настройками подключения» (`native.pickBundle`, `ACTION_OPEN_DOCUMENT`, `*/*`).
Ввод текстом не годится: `input text` прислал 2612 символов, в поле осело 515.
Скриншоты приложения чёрные (окно с `FLAG_SECURE`) — все проверки UI сделаны по `uiautomator dump`.

### 2–6. Туннель

Подключение шло через **статический AWG** (профиль «Мой AmneziaWG», слот 5):
«Интерфейс активен», «Туннель активен · DNS через туннель», счётчики растут,
на сервере свежий handshake (`wg show xioawg0 latest-handshakes` = `1793784286` при
серверном времени `1793784316` → 30 с).

Первый замер `ping -c 3 1.1.1.1` сразу после подключения дал 0/3 — через ~40 с тот же
пинг 3/3 с 34–52 мс. То есть сразу после установления туннеля есть короткое окно,
когда ICMP ещё не проходит (TCP в это время тоже не проходил: `nc` timeout).

Проверка 6 выполнена через временный HTTP-сервер на бридже (`python3 -m http.server 8099`,
файл 1 400 000 Б, после замера сервер и файл удалены). Это позволило обойтись без TLS:
`curl`/`wget` на устройстве отсутствуют, а `speedtest.tele2.net` по HTTP не ответил (0 Б).

Скрипт `cycles2.ps1`: тап по кнопке подключения → ожидание «Интерфейс активен» по дампу →

нулевые ошибки и PSS.

На 0.24.2 процесс выжил 20 циклов при 551 МБ PSS.

### 8. Транспорт

Ручной выбор протокола в Full-приложении отсутствует (в клиентском `client_main.dart` список
плоский, в Full — группировка по `serverId`): в шите «Серверы и подключения» ровно две строки —
сервер бандла (rivet, `:8443`) и статический AWG (`:51821`), выбрать `awg`/`rivet-h3`/`rivet-s1`/`xray`
одного сервера нельзя. По критерию координатора это «не поддержано», а не дефект.

Авто-fallback проверен закрытием AWG на бридже (временная nft-таблица `inet xioe2e`:
`udp dport 51821 drop` + `iifname xioawg0 drop`, снята после теста):

```
T0 12:52:06.680 block applied
T=+  3,9s AmneziaWG 3.1 1     (UI ещё считает, что туннель жив)
T=+167,5s AmneziaWG 3.1 0     (только здесь UI заметил)
T=+  214s RIVET / S1 1        FAILOVER
```

**Дефект D2 (major).** 214 с вместо ≤30 с. Watchdog (`core.dart:1906–1931`) пробует
`InternetAddress.lookup('example.com')` раз в 15–30 с и требует двух промахов подряд;
ответ, судя по задержке, приходит из DNS-кэша, поэтому мёртвый транспорт замечается
только через ~167 с. Прямой пробы data-path (TCP/ICMP через туннель) у watchdog нет.

После снятия блокировки приложение осталось на RIVET/S1 (обратного переключения нет — ожидаемо).

### 9. Авиарежим

`cmd connectivity airplane-mode enable` → 60 с → `disable`. Восстановления не было:
в опыте на 0.24.2 интерфейс не вернулся за 125 с, спустя ~10 минут состояние «Отключено».
На 0.24.1 тест невалиден (см. таблицу). Отдельно отмечу: пока туннель был выключен,
`ping 1.1.1.1` шёл напрямую через Wi-Fi — то есть проверять восстановление по ping нельзя,
только по состоянию интерфейса и свежему handshake.

## Что не удалось

1. **IPv6 (проверка 4) — невыполнима в этой среде.** На бридже нет IPv6-аплинка:
   `tun0` отсутствует («Device "tun0" does not exist»), `ip -6 route` без default,
   у `enp3s0` только link-local. Ожидаемый exit `2a0c:b641:1a0:800::2a2` недостижим.
   При этом сервер отдаёт `rivet.ipv6 = true` (из `network.dualstack().capabilities()`),
   и приложение честно кладёт в профиль `DNS = 9.9.9.9, 2620:fe::fe` → резолвер Android
   виснет. Комментарий в `app/lib/managed_models.dart:7-8` описывает ровно этот случай,
   то есть флаг возможностей был устаревшим на момент выдачи профиля.
2. **Число fd** — без root не читается (см. выше), метрика заменена косвенными.
3. **Авиарежим** — самовосстановление не подтверждено ни на одной сборке.
4. **Ручное переключение транспорта** — функции нет в 0.24.x Full.
5. **Повторный прогон «чистых» 20 циклов на 0.24.1** не сделан: на 14-м цикле процесс
   убит, а окружение параллельно менялось (см. «Ограничения среды»).

## Резюме для xio (5–10 строк)

1. fd-фикс работает: 33 цикла connect/disconnect на 0.24.2 и 0.24.1 — **ноль** `bad file descriptor`/`EADDRINUSE`/`too many open files`, каждый цикл свежий handshake, pid стабилен на 0.24.2.
