## 3. Найденные и исправленные дефекты

### 3.1 Правила nat без комментария (нарушение рецепта)

До работы на сервере уже стояли правила, оставшиеся от ручной попытки:

```
-A PREROUTING -i awg0 -p tcp -j REDIRECT --to-ports 19192        ← без комментария
-A PREROUTING -i awg0 -p udp -m udp --dport 53 -j REDIRECT --to-ports 5353
```

`vpn4-rules.sh` теперь сначала удаляет нетегированные дубликаты **на своём интерфейсе**, затем
добавляет тегированные и в конце проверяет `iptables -C` + `ip -4 addr show` — юнит падает,
если правило или адрес не применились, а не делает вид, что всё хорошо.

### 3.2 Ошибка порядка байт в `SO_ORIGINAL_DST` (реальный баг старого бинаря)

В старом бинаре семейство адреса читалось как big-endian:

```
vpn4: drop 10.81.0.1:45794: SO_ORIGINAL_DST returned family 512, not AF_INET
```

`sin_family` в `struct sockaddr_in` — **host order** (на x86 `02 00` = 0x0200 = 512), порт и
адрес — network order. Исправлено:

```go
family := *(*uint16)(unsafe.Pointer(&sa[0]))   // host order, не binary.BigEndian
```

Найден именно изолированным тестом нового бинаря (порт 19193, отдельный OUTPUT-REDIRECT на
`1.1.1.1:80`), до замены рабочего бинаря —production путь при этом не прерывался.

## 5. Инцидент с `/etc/resolv.conf` (важный урок рецепта)

На момент начала работы `/etc/resolv.conf` содержал `nameserver 10.90.0.1` — адрес сервера
**в туннеле**, где на 53 ничего не слушает. Следствие: DNS на сервере не работал вообще
(`10.90.0.1#53: connection refused`, `getent hosts example.com` → пусто).

Причина: предыдущий прогон теста выполнял

```sh
nsenter -t $NS_PID -n sh -c 'echo "nameserver 10.90.0.1" > /etc/resolv.conf'
```

Сетевой namespace **не** изолирует mount namespace, поэтому запись ушла в файл **хоста**.
Прежнее содержимое файла нигде не сохранилось (бэкапа не было), RA от провайдера не содержат
RDNSS (5 минут `tcpdump 'icmp6 and ip6[40]==134'` → 0 пакетов), поэтому исходный адрес был
восстановлен по факту: `2a01:4f8:c2c:123f::1` — единственный DNS, который отвечает с этого
хоста и является DNS64 (отдаёт `ipv4only.arpa` → наш префикс). Файл сейчас содержит
`nameserver 2a01:4f8:c2c:123f::1`, сломанная версия сохранена как
`/etc/resolv.conf.broken-20261105`.

**В `vpn4-rules.sh` и `e2e-netns-test.sh` записи в `/etc/resolv.conf` нет** — DNS клиента
проверяется через `dig @10.90.0.1`, файл хоста не трогается. Предупреждение вынесено в
`deploy/nat64/README.md`.

## 7. Ограничения

- Только **TCP** и **UDP/53**. QUIC/HTTP-3 и прочий UDP через мост не пойдут (REDIRECT UDP в
  userspace без полного NAT-состояния не сделать); браузеры откатятся на TCP.
- **ICMP отсутствует** — `ping -4` из туннеля не работает (проверено, 100% loss). Значит,
  `traceroute`, PMTU-обнаружение через ICMP и `ping` недоступны.
- Endpoint туннеля остаётся IPv6 (`[2a0c:b641:1a0:800::2a2]:51830`) — клиент обязан иметь IPv6.
- Выходной IPv4 = адрес провайдерского NAT64 (`159.69.108.193`), он общий для всех наших
  соединений; это не «свой» IPv4 и он может измениться у провайдера.
- DNS-релей форвардит на `1.1.1.1:53` (plain DNS), без кэша; один запрос = один UDP-сокет.
  DNS64 клиентам теперь не нужен — у них есть настоящий IPv4.
- Поддерживается один IPv4-клиент (`10.90.0.2/32`). Второй клиент — второй адрес и второй
  `/32` в `AllowedIPs` (установщик принимает `CLIENT_V4` аргументом, но мультипировый сценарий
  не тестировался).
- Один клиент = один набор правил; при нескольких интерфейсах (`awg4`) нужен повторный запуск
  установщика с другим `AWG_IF`. Второй интерфейс не создавался: существующий `awg0` принял
  IPv4 без поломки сервиса.
- Живая нагрузка: на момент проверки через мост шёл реальный трафик телефона (~230 МиБ),
  но нагрузочного теста (тысячи одновременных соединений) не было.
- **Не все IPv4-адреса достижимы через провайдерский NAT64.** В журнале есть честный отказ:

  ```
  tcp client=10.90.0.2:60526 dst=188.72.108.93:443 -> [2a01:4f8:c2c:123f:64:5:bc48:6c5d]:443
      FAIL dial tcp6 […]:443: i/o timeout
  ```

  Это ограничение NAT64 (у провайдера нет трансляции/маршрута к части сетей), а не моста:
  мост корректно сообщает об ошибке и закрывает соединение. Диагностируется по строке `FAIL`.

## 8. Откат

```sh
systemctl disable --now vpn4 vpn4-rules
rm -f /usr/local/bin/vpn4 /usr/local/sbin/vpn4-rules.sh /etc/xio-vpn4.conf
rm -f /etc/systemd/system/vpn4.service /etc/systemd/system/vpn4-rules.service
systemctl daemon-reload
# снять только свои правила
iptables -t nat -S PREROUTING | grep xio-vpn4 | sed 's/^-A /-D /' \
  | while read -r r; do iptables -t nat $r; done
iptables -S FORWARD | grep xio-vpn4 | sed 's/^-A /-D /' | while read -r r; do iptables $r; done
ip -4 addr del 10.90.0.1/24 dev awg0            # по желанию
mv /etc/awg-owner/awg0.setconf.conf.bak-xio-vpn4 /etc/awg-owner/awg0.setconf.conf
mv /etc/awg-owner/client-ipv4.conf.bak-xio-vpn4 /etc/awg-owner/client-ipv4.conf
systemctl restart awg-owner
```

Автоматический вариант: `deploy/nat64/README.md`, раздел «Откат».

## 9. Что не проверено

- **Перезагрузка сервера** (запрещена условием) — автозапуск после ребута не проверен,
  только логика: оба юнита `enabled`, `vpn4-rules` стоит `Before=vpn4` и переприменяет
  правила, `apply.py` возвращает адрес на `awg0` при каждом старте `awg-owner`.
- Второй/третий клиент AWG одновременно, мультипировый сценарий.
- Долгоживущие TCP-соединения под нагрузкой (idle-timeout моста 10 мин задан, но не
  испытан на реальном долгом соединении; в журнале видны сессии до ~10 минут).
- IPv4-UDP кроме 53 (не поддерживается by design), ICMP (не поддерживается by design).
- Поведение при смене префикса/адреса DNS64 провайдером (префикс задаётся аргументом
  установщика и хранится в `/etc/xio-vpn4.conf`).
- `sshpass` на Debian и сам маршрут `ssh debian17 → VPS`: SSH на Debian не отвечает,
  работа шла прямым подключением к прокси-порту 9046.
- Зона sibling-агента (каскад `xio-nat64-exit`, `tun0`, `10.200.0.0/30`) — **не моя зона**,
  её работоспособность я не проверял; убедился только, что наши правила и порты не конфликтуют
  и что его трафик проходит через наш `vpn4` (видно в журнале).
