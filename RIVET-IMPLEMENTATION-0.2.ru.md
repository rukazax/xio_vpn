# RIVET/1: профиль реализации 0.2

Инженерная реализация, не криптографический аудит и не стандарт. Дополняет историческую архитектуру0.1; отличия ниже явные. Цель выпуска — рабочий клиент/шлюз и воспроизводимые отрицательные и сетевые испытания, а не обещание абсолютной необнаруживаемости.

## Замороженная совместимость

- S1: HTTPS/WSS с честным внешним ALPN http/1.1, путь `/api/stream`, двоичные сообщения без сжатия, затем независимый внутренний TLS1.3 с ALPN `rivet/1`.
- H3: HTTP/3 CONNECT-UDP RFC9298 и RFC9297 через masque-go, только фиксированный адрес разрешённого шлюза. Внутри — QUIC/TLS1.3 с ALPN `rivet/1`, управляющий stream (клиент сначала передаёт байт preface `00`, затем сервер CHALLENGE) и QUIC DATAGRAM RFC9221. Внешние начальные пакеты1450байт, внутренние1200. При непригодном UDP/PMTU — следующий транспорт; поддержка уменьшенного PMTU не имитируется отключением проверки или криптографии.
- Внутренний обмен только X25519MLKEM768, без 0-RTT, resumption и понижения группы. Сервер аутентифицируется независимым SHA256 SPKI pin, дополнительно проверяется срок сертификата. Аутентификация сервера остаётся классической ECDSA P-256: постквантовая аутентификация не заявляется.
- **Изменение относительно0.1:** используется штатный набор AEAD TLS1.3 сопровождаемой Go crypto/tls, включая AES-128-GCM. Стандартная Go crypto/tls не позволяет задавать TLS1.3 CipherSuites через Config. Скрытая модификация stdlib/unsafe linkname не применяется. Нельзя называть весь профиль «256-битным» или гарантировать постквантовую стойкость AEAD. Согласованные версия, группа и cipher suite фиксируются в тестовых доказательствах.
- **Изменение относительно0.1:** вместо короткоживущего admission ticket пока используется постоянный, отзываемый вместе с пользователем входной токен. Кража токена позволяет обратиться к внутреннему шлюзу, но не заменяет K_device и pin. Автоматическая ротация токена не реализована.
- Отдельные случайные секреты устройства и входа, по32байта. На входе хранится SHA256 входного токена, а не K_device. Устройство доказывает знание K_device через HMAC-SHA256 из архитектуры0.1, привязанный к nonce, gateway_id, TLS exporter и точным параметрам. Gateway хранит AES-GCM sealed секреты, ключ хранения расположен отдельно от БД; сам gateway доверенный и способен их расшифровать.
- AUTH параметры: deterministic CBOR `{0:1,1:carrier,2:1,3:1280}`. carrier0=H3,1=S1. Стороны сравнивают с точным каноническим кодированием. Адрес и CONFIG фиксированы профилем; клиент не принимает произвольные маршруты/DNS от входа.
- Заголовки stream, типы и CONFIG соответствуют архитектуре0.1. До AUTH/config ACK пакеты не маршрутизируются. Неожиданный тип в любом состоянии закрывает сеанс.
- **IPv4-only:** TUN MTU1280; адрес10.79.0.slot/32, маршрутизация0.0.0.0/0. Wire CONFIG сохраняет DNS1.1.1.1 для совместимости профиля0.2; Android применяет собственную локальную политику DNS9.9.9.9 вместо предлагаемого DNS. Значение из CONFIG не используется для произвольной настройки системного resolver. IPv6 захватывается/блокируется клиентом, а не выходит напрямую. IPv4 options, фрагменты и неизвестные IP-протоколы не поддерживаются. Это ограничение реализации, не dual-stack VPN.
- H3 фрагментирует IP по1000байт; формат из0.1. Не более64 незавершённых пакетов, срок1с, максимальный пакет1280байт, окно повторов4096. Частичные перекрытия/изменение длины отвергаются; одинаковые дубли игнорируются. Пределы проверяются до выделения буфера.
- Источник пакета обязан совпадать с выданным адресом. Loopback, RFC1918, link-local, metadata, CGNAT, multicast, benchmarking и адреса самого gateway запрещены. Это VPN для публичного интернета, а не доступ к частным подсетям.
- Отзыв закрывает действующий сеанс в пределах5с и запрещает новый. Одно действующее соединение на пользователя/IP. Новое аутентифицированное соединение заменяет старое; чужой пользователь не может занять этот адрес.

## Эксплуатационные границы

Вход и gateway разделены процессами, файлами ключей и системными пользователями. На одном VPS это не защищает от компрометации root/гипервизора. Внешний TLS использует нормальную проверку PKI, без InsecureSkipVerify. Если на VPS уже есть подходящий действующий публичный сертификат, установщик использует его локальную копию, не извлекая закрытый ключ на клиент. Иначе генерируется отдельный CA, закреплённый только в конкретном профиле. Это даёт аутентификацию, но приватный сертификат заметно отличается от обычного публичного сайта. Автоматическое продление внешнего сертификата пока отсутствует: публичную копию нужно обновить до истечения срока, приватный сертификат рассчитан на90дней, внутренний —180дней. Внутренний pin нельзя заменять проверкой внешнего сертификата.

Нормальный сайт и стандартный HTTPS/HTTP3 уменьшают простые отличия, но Go ClientHello, долгие двунаправленные потоки, порт, объём и тайминги могут отличаться от браузера. Проверка pcap/классификатора не доказывает неразличимость для всех операторов. IP/ASN-блокировка, allowlist-only сеть и глобальная корреляция остаются вне гарантий.

На Android собственное восстановление RIVET должно сохранять TUN и блокировать пакеты, пока нет защищённого сеанса. Для полного отсутствия окон выхода вне VPN при переключении **между разными движками**, принудительной остановке и перезапуске ОС требуется штатный Android Always-on VPN + «Блокировать соединения без VPN»; приложение без системных прав не может молча включить этот параметр. Это проверяется отдельно и не подменяется успешным HTTPS-запросом.

## Нормативные источники

- [Go crypto/tls Config](https://pkg.go.dev/crypto/tls#Config): TLS1.3 cipher suites задаёт библиотека.
- [RFC9298](https://datatracker.ietf.org/doc/html/rfc9298): CONNECT-UDP.
- [GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932): предупреждение об OpenPGP в транзитивном модуле x/crypto; пакет не импортируется и не вызывается данным кодом.

Порядок автоматического выбора без другого выбранного приоритета: H3 → S1 → AmneziaWG → WireGuard. RIVET ограничивает handshake оставшимся временем пользовательской попытки, с собственным потолком10с. Системное разрешение VPN не включено; задержки запуска/остановки служб ОС могут добавлять время; разрешение имени импортированного endpoint и handshake делят один бюджет. Существующий сеанс RIVET восстанавливается отдельно с паузами1/2/4/8с. Проверка живости — каждые10с при пороге25с; фактическое обнаружение молча пропавшего канала возможно до≈30с, это отличается от тайм-аута первоначального подключения.
