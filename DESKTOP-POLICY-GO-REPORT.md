## Implemented

- **Immutable plan v2** (`internal/desktop/policy.go`): exact 14-key object, no unknown/duplicate keys, `schema==2`, `profiles[]={id,protocol,endpoint,configDigest}`, `routing` must be JSON `null` on desktop (non-null = `POLICY_INVALID`, never ignored), `priorityProtocol` exact string or null, `policy{mode,roundMillis:30000}`, manual = exactly `selectedId` + one entry (malformed multi-id rejected, never truncated), automatic keeps selected first, ≤16 candidates, canonical replay fingerprint. `configDigest` is lowercase hex SHA-256 of the exact UTF-8 base config bytes; the four parent-verified WIRE-V2 goldens are asserted verbatim (trailing-LF pair, vless JSON, empty).
- **Policy RPCs** in the existing authenticated dispatch: `policyCapabilities`, `policyState`, `policyBegin`, `policyCommit`, `policyReconcile`, `policyAbort`. Begin/commit/reconcile accept exactly the eight agreed keys; abort accepts exactly the three-key revocation request `{version, instanceNonce, transactionId}`; the transport rejects any extra/missing top-level key. ACK is exactly six keys. Errors use the existing envelope with exact codes `POLICY_INVALID`, `POLICY_UNSUPPORTED`, `POLICY_BUSY`, `POLICY_STALE`, `POLICY_UNKNOWN`.
- **One serialized writer** inside the existing Runtime: every policy mutation happens under the Runtime mutex; the only physical step (read-only resource observation) runs outside it while the writer lane stays owned. `policyAbort` marks the logical revoke, waits for an in-flight observation to settle (bounded, ownership retained) and only then writes the blocked receipt. A late commit/reconcile cannot resurrect readiness; an exact same-content retry of a committed transaction is idempotent; anything else needs a fresh transaction.
- **Readiness is honest**: a fresh helper starts `blocked` with `resourceState:"unknown"`. READY is ACKed only after `policyReconcile`/`policyCommit` with `clean` evidence; `owned` yields a blocked ACK with an explicit recovery expectation, a failed/unsafe query yields `unknown`; nothing is ever deleted or repaired. Desired next state is `clean → ready`; the known-clean path is `policyCapabilities → (launch-bound, shared-claim) reconcile → READY`.
- **Two cooperating claims** (`helper_claim*.go`): a per-store claim (`/run/xio-policy-<store>.lock`, `ProgramData\XIO\policy-<store>.claim`) and a shared fixed-resource namespace claim (`/run/xio-resource-xio019.lock`, `ProgramData\XIO\resource-xio019.claim`). Both are process-lifetime; the resource claim is taken unconditionally at startup and is what prevents two helpers with different Full/Client store identities from both observing clean and both activating. Linux uses `flock`; Windows uses an exclusive-share file (a mutex was rejected: ownership is thread-affine and a Go goroutine's OS thread can exit). Tests inject owned fixture claim files and prove exclusion + handover with distinct store IDs while both observe clean.
- **Launch binding is mandatory for versioned work**: the helper never adopts `storeIdentity` from an RPC; the launch `--store-identity` value must equal the RPC store. Versioned RPCs and receipt activation additionally require the shared resource claim (`POLICY_UNSUPPORTED` otherwise). A bound helper never accepts receipt-free legacy connects. The only remaining legacy window is genuinely unbound/unclaimed-versioned helper state (no store binding, commit, pending transaction or writer).
- **Activation fence** (`ConnectWithPolicyReceipt`): `PolicyReceiptJSON` is the six-field attachment as a JSON string on the existing capitalized request. Under the Runtime mutex, before any admin/stop/setup/route effect, the helper re-derives `sha256(exact raw config bytes)` and compares store/instance/controller/transaction/generation plus candidate membership, manual selection and protocol. Divergence is `POLICY_STALE` with zero effects (tests assert prepare/start counters stay 0 for trailing-LF, trimmed and reformatted variants); missing receipt after versioned ownership began is `POLICY_UNSUPPORTED`. `connect` still re-hashes the actual bytes regardless of validation state.
- **Resource evidence** (`policy_evidence*.go`), read-only: Linux `/run/xio-client.lock` ownership journal (exact marker or empty; regular, root-owned, 0600, single link), `xio019`, reserved rule priorities 18018/18019, dedicated table 28691 / `dev xio019`; Windows held `tunnel.lock` (sharing violation = owned), exact legacy firewall receipt, leftover `sharing.json` receipt, `xio019`. Enumeration failure or an unsafe/malformed artifact is `unknown`, never `clean`; no observer writes or deletes.
- **`policyState` diagnostics are finite and nonsecret**: `error` ∈ {"", "revoked", "resource_owned", "resource_unknown"}, `pendingTransaction` string|null, `launchBound`, `resourceClaimed`, `storeIdentity`, `planSchema`, `resourceState`, `state`. The six-field `receipt` is present only while `state=="ready"`; while blocked/pending only `casGeneration` (expectedGeneration CAS input) is exposed, never activation authority.

## Known limits / blocked

- **No Windows execution proof**: App Control blocks unsigned Go; only `GOOS=windows` build/vet. The Windows claim/evidence code is type-checked, not executed. No real helper launch, elevation, VPN, TUN, route, firewall, service or credential was exercised anywhere.
- **READY does not prove vault provenance**: the helper cannot read the Dart vault or the durable document from the current wire, so it cannot verify at commit that the supplied digests came from the product store. It verifies supplied bytes when a validation bundle is provided (extension proposed below) and always re-hashes the actual connect bytes before effects. Provenance rests on the controller + Store writer lock and readback.
- **No durable helper plan journal** (by design, DESIGN §5): helper readiness is memory-only; a restart yields a new instance nonce and a blocked helper until an explicit reconcile. `policyState` keeps the committed generation only as a CAS input.
- **Coordination pending**: `policyValidate` schema/state transitions (below) need parent/core agreement before coding; `policyState`/`policyCapabilities` must not emit a `validation` field until the other parsers accept it. Bridge must pass `--store-identity` on every policy-capable launch, read `instanceNonce` from `capabilities`, discard cached receipts on restart, and reconcile the exact durable snapshot before activation; a second helper start fails the claims and must not be retried blindly.
- Residual legacy window: an unbound, never-claim-bound helper still accepts receipt-free legacy connects until versioned ownership begins; the bridge must not send them when the durable document carries `connectionPolicy`/`connectionPlanReceipt`/pending state.

Freeze status: `dfd2710` is recorded as the frozen slice but NOT accepted, because helper-side validation is still missing. `ee9f527` (legal-record helper with the uppercase-Z-only timestamp rule) is HELD: that rule was not parent-verified and is corrected by the Dart 3.13.5 probe results recorded below; the helper is still unwired, so there is no integration impact.

## Candidate-order oracle (re-derived exactly) and timestamp grammar

The eligibility order is now the accepted Store oracle, not an approximation:
- `protocolPreference(protocol, priority, restricted:true)` mirrors `rivet_profile.dart` with `restrictedNetworkProtocols = [xray, rivet-s1, cloak, awg, rivet-h3]`; the selected/explicit priority protocol ranks 0, the documented order 1..5, unknown 100.
- `connectionCandidates` is re-derived: revoked owner → no candidates; selected first when usable; same-endpoint variants sorted by preference with document order only as the tie-break; other-endpoint fallbacks the same way; `clientOnly`/owner filter and the helper's own supported-protocol list gate the pool; the offered `ids` must be an ordered subsequence of this derived order (dropped unreadable non-selected candidates remain legal). The first owner whose `profileIds` values contain the selection is used, matching `firstOrNull`.
- Golden: same-endpoint AWG+AWG+XRX document in plain document order, default `xray` priority → the plan in document order is rejected and the preference order is accepted; explicit `priorityProtocol=awg` inverts the intra-group order and the reciprocal plan is rejected; a dropped candidate remains valid.
- Exact mixed-protocol oracle (accepted source `connection_plan_test.dart`, document order `awg1,x2,x3,r3,c4,h5,o6`, preferred `rivet-h3`): the Go oracle produces and accepts `[awg1, h5, x2, x3, r3, c4, o6]`, rejects source order, fallback-before-variant, xray-after-rivet-s1, inverted tie order and variant-ahead-of-preference permutations, accepts the dropped-candidate subsequence, and asserts the preference table (rivet-h3 0, xray 1, rivet-s1 2, cloak 3, awg 4, unknown 100). The ordering function takes the supported-protocol set as a parameter; production passes the helper's own list (cloak is not a desktop protocol, so a real desktop plan cannot contain it), while the oracle test passes the accepted five-protocol set to cover cloak.
- Oversize handling stays local: the helper rejects oversized validation payloads with `POLICY_INVALID`; the `POLICY_OVERSIZE` controller-preflight enum is not adopted into the RPC wire without an explicit agreement. The controller must preflight the size caps before its irreversible rename.

`legalTimestampIsUTC` now copies the **exact** `_parseFormat` of the installed Dart 3.13.5 SDK (`lib/core/date_time.dart`, BSD-style SDK header, kept in the parent's source copy): `^([+-]?\d{4,6})-?(\d\d)-?(\d\d)(?:[ T](\d\d)(?::?(\d\d)(?::?(\d\d)(?:[.,](\d+))?)?)?( ?[zZ]| ?([-+])(\d\d)(?::?(\d\d))?)?)?$`. Date separators and time colons are optional, so compact forms (`20261106T090000Z`, `2026-11-06T090000Z`, `20261106T09:00:00Z`, `20261106T0900Z`, mixed separators) are accepted naturally — not a whitelist. The predicate returns `parts[8] != ""`, exactly `parse`'s `isUtc = group8 != null` rule; it adds no RFC or Go-DateTime range restrictions (Dart normalises component overflow and the runtime's match/isUtc behaviour is what the oracle records). The reviewer's Dart-generated probe `review_timestamp_test.go` (SHA-256 `fec8d88bd8ed55a4bf98d2ab00634864e7f3208a854c9cd7fd920d9642718641`) with `review_timestamp_oracle.json` (SHA-256 `5369bb6057e9dcfcb6d70a37f776621ed78dec13ad150bee0b701659713b0316`, produced by the installed Dart 3.13.5) reproduced the three compact-form failures on `75ca97b` and passes unchanged on this candidate; positive controls `2026-11-06T09:00:00Z`, the nine-digit fraction, `999999-…` and `+999999-…` remain green through actual `validate → reconcile`. The stored bytes are never normalised before hashing. The forwarded fix is the commit containing this report (product base `75ca97b`, only this timestamp grammar patch plus tests; the earlier probe/report artifacts stay untracked).

### Finish-parse range admission (same forward fix)

Regex match alone is not enough: the installed VM `_finishParse` rejects a parsed value when `_brokenDownDateToValue` exceeds `_maxMillisecondsSinceEpoch * microsecondsPerMillisecond` (`8640000000000000 * 1000`). The helper now mirrors that actual implementation: `dartBrokenDownMicroseconds` performs the same zero-based month normalisation (Dart Euclidean `%`, truncating `~/`), `_DAYS_UNTIL_MONTH` leap table, `_dayFromYear` with `_flooredDivision`, fraction-to-millisecond/microsecond conversion, timezone minute adjustment from `parse`, and the `abs(value) > bound` rejection using **Dart VM signed-64 wrapping arithmetic** (Go int64 wraps identically), not a Go-DateTime year clamp. Consequently the reviewer boundary `275761-01-01T00:00:00Z` is rejected (actual Dart `isUtc=false`), while the seven compact/positive controls — including `2026-11-06T09:00:00Z`, the nine-digit fraction and `999999`/`+999999` years, which wrap back into range — remain `isUtc=true` and reach `READY`. The reviewer's `review_timestamp_range_test.go` (SHA-256 `8f3264ab21fe0186e205be16968f43f000fbe9b94626fdaa9eb1934bcd254967`) and `review_range_oracle.json` (SHA-256 `7636347c8e5478ae57cb36ef3360ae354307df79b1b0572eda3200bf2c592ee0`, from actual Dart oracle SHA `2d291897…`) were copied unchanged; on `fbaa4d8` they reproduced the false positive (`validateACK` digest `e1254987…`, then `reconcile` `READY`) and on this candidate the range probe passes together with the unchanged seven-case probe.

Configuration blankness uses the same Dart contract: `dartBlank` implements the probed `String.trim()` matrix (blank = U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028, U+2029, U+202F, U+205F, U+3000, U+FEFF; non-blank = U+0000, U+001C–U+001F, U+180E, U+200B). Go's `strings.TrimSpace` misses U+FEFF, so the helper would otherwise accept a BOM-only configuration; the predicate is tested against the full matrix plus mixed blank/non-blank controls and a Dart-blank-only config rejection. This is the only basis for any "accepts Dart-canonical configs" claim: the parser accepts the grammar and blankness above, not arbitrary Dart-valid strings beyond it.

Controller-side boundary reported to core: the helper can only reject an oversized validation snapshot after the controller has already read/renamed it; the controller must preflight the document/config size caps before the irreversible rename, otherwise an old valid store can be stranded. Profile/document size caps remain provisional.

Honest limits of this validation: the helper proves consistency of the supplied snapshot (document bytes, config bytes, plan, receipt, consent record, eligibility/order), not vault or filesystem provenance; the controller's Store writer lock and readback vouch for provenance. Config bytes are kept only transiently for hashing/parsing; no logging or persistence; best-effort zeroing only. The fixture's `parserAcceptance` metadata sits outside the actual request and is ignored by the helper; the request is exactly the nine keys.
