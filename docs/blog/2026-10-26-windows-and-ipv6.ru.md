# XIO Client 0.22.5: нативная проверка Windows, IPv6 на тестовом стенде

Дата: 26.10.2026. Релиз 0.22.5+5014 продолжает линию 0.22.4 и закрывает два дефекта, найденных
на реальном оборудовании, а не в тестах.

## Что проверено на этом прогоне

Стенд: Debian 13 (`192.168.88.17`) + физический POCO X6 5G (Android 16) + Windows 11 x64.
Сервер поднят штатным бандлом приложения (recipe 24), клиент собран из исходников с подписью
издателя.

| Что | Результат |
|---|---|
| Android, AmneziaWG, IPv4-endpoint | подключение, HTTP 200, трафик |
| Android, AmneziaWG, IPv6-endpoint | подключение, HTTP 200, `ping6` до шлюза туннеля 0% потерь |
| Android, RIVET/H3 и S1 | подключение, HTTP 200, 31.0/18.9 КБ, сервер видит пользователя online |
| Android, Xray/REALITY | **не подключается** — см. ниже |
| Windows x64, AmneziaWG | нативный туннель Wintun: адаптер `xio019`, адрес 10.78.0.7/32, ping 3/3, handshake, 496 КБ принято / 2.9 МБ передано |

## Дефект 1: повторный импорт профиля после удаления

Удаление профиля оставляло в записи пользователя ссылку на несуществующий профиль, из-за чего
повторный импорт того же `xio://` контейнера отклонялся как «Пользователь уже добавлен» — хотя на
устройстве профиля уже не было.

Исправлено в `app/lib/core.dart`: удаление профиля теперь снимает ссылку у всех пользователей и
откатывается снимком состояния при ошибке записи. Заодно `forgetServer()` и `revoke()` итерируют
копию коллекции, иначе удаление внутри цикла ломало её.

Добавлен регрессионный тест `app/test/profile_removal_test.dart`: он падает на прежнем коде и
проходит на исправленном.

## Дефект 2: правило firewall для IPv6 на Windows

Для блокировки IPv6-трафика при активном туннеле helper вызывал
`netsh advfirewall firewall add rule ... remoteip=::/0`. На актуальной Windows 11 netsh отвергает
префикс нулевой длины (`Один или несколько префиксов адресов недопустимы`), из-за чего подключение
падало с «Windows VPN firewall setup failed» — то есть Windows-клиент не подключался вообще.

Проверено вручную: `remoteip=::/0` и `remoteip=0.0.0.0/0` отклоняются, а `remoteip=::/1,8000::/1`
принимается и покрывает тот же диапазон. Исправлено в
`protocol/rivet/internal/desktop/network_windows.go`.

## Ограничение, которое не исправлено: Xray/REALITY

Сервер (Xray `26.7.28`) отвечает `REALITY: processed invalid connection … handshake did not
complete successfully`, клиентское ядро — форк `amnezia-xray-core v1.260728.0`. Ключи REALITY,
`shortId` и `serverName` сверены и совпадают; понижение `minClientVer` до `1.0.0` не помогает.
Значит несовместима сама реализация REALITY, а не одна проверка версии. До выравнивания ядер
считать Xray рабочим на этой паре «клиент + шлюз» нельзя. AWG и RIVET работают.

## IPv6: что именно проверено

Публичного IPv6 в тестовой сети нет (маршрутизатор не раздаёт префикс), поэтому использован
локальный ULA `fd88:17::/64` с анонсом через radvd и без default-route — телефон получает адрес,
интернет-путь не меняется. Подтверждено: клиент подключается по `[fd88:17::1]`, внутри туннеля
получает `fd78:1::N/128`, `ping6` до шлюза туннеля проходит.

Выход IPv6 наружу при этом заблокирован самим сервером (`ip6tables FORWARD -i x1oawg0 -j DROP`,
NAT66 нет) — это осознанное поведение, а не дефект, но публичным dual-stack его считать нельзя.

## Что дальше

- Выровнять ядро Xray (клиент/шлюз) или явно исключить Xray из заявленной матрицы до проверки.
- Проверить подключение на Windows через графический интерфейс целиком (в этом прогоне движок
  проверен по тому же IPC-протоколу, которым пользуется интерфейс).
- Разобраться с сосуществованием двух VPN на одной машине: при активном стороннем VPN с
  маршрутами `/1` туннель XIO поднимается, но рукопожатие не проходит.
