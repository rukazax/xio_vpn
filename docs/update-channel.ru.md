# Канал автообновления XIO: выпуск и проверка

[English](update-channel.en.md) · [Обновления для пользователя](ru/updates.md) · [Сборка](ru/build.md)

Канал обновлений приложения был мёртв с 0.22.2: релизы `v0.23.0`, `v0.23.1`, `v0.24.0`,
`v0.24.1` и `v0.24.2` не содержали ассета `XIO-update.json`, поэтому приложение не
предлагало обновиться ни на одной платформе. Здесь описано, как устроена проверка, как
выпустить манифест и что видит пользователь, если манифеста нет.

## Что именно читает приложение

```mermaid
flowchart TD
    A[Наступил срок или нажата кнопка] --> B[GET api.github.com/repos/rukazax/xio_vpn/releases?per_page=30]
    B --> C{Есть тег vX.Y.Z новее установленной версии?}
    C -->|Нет| D[Следующая проверка через 7–8 суток]
    C -->|Да| E{В релизе ровно один ассет XIO-update.json?}
    E -->|Нет| D
    E -->|Да| F[GET манифеста по browser_download_url]
    F --> G[Ed25519-подпись закреплённым ключом + разбор payload]
    G --> H{tag совпадает, build больше установленного?}
    H -->|Нет| D
    H -->|Да| I[assets[platformKey] → размер и SHA-256]
    I --> J[Скачивание после согласия пользователя]
    J --> K[Проверка размера и SHA-256 → установщик ОС]
```

Источник истины — код: `app/lib/update_service.dart` (`_check`, `verifyReleaseEnvelope`,
`XioRelease`, `UpdateAsset`, `validateAssetUrl`), `app/lib/update_installer.dart`
(распаковка/установка), `app/lib/update_ui.dart` (диалог). Версия и номер сборки — только
`app/lib/version.dart` (`xioVersion`, `xioBuild`); `app/pubspec.yaml` должен совпадать с ним.

Ключевые ограничения, которые проверяет клиент (манифест, нарушающий их, будет молча
отброшен):

| Поле | Требование |
|---|---|
| конверт | `{"payload": base64(JSON), "signature": base64(64 байта Ed25519)}` |
| `payload` | не больше 64 000 байт |
| подпись | Ed25519 ключом, открытая часть которого зашита в `app/assets/security/update-ed25519.pub` |
| `schema` | ровно `1` |
| `tag` | `vX.Y.Z`, и `tag == 'v' + version` |
| `version` | `X.Y.Z`, строго новее установленной (иначе релиз пропускается) |
| `build` | целое ≥ 1, строго больше установленного `xioBuild` |
| `notes` | строка не длиннее 12 000 символов (полные заметки релиза туда не влезают) |
| `assets` | хотя бы одна платформа; `url` — HTTPS только на `github.com`, префикс пути `/rukazax/xio_vpn/releases/download/<tag>/`, без порта, userinfo, query и `..` |
| `sha256` | 64 символа нижнего регистра |
| `size` | 1 … 800 МиБ |

Платформенные ключи, которые запрашивает приложение (`UpdateService.platformKey`):

| Ключ | Платформа |
|---|---|
| `android-arm64-v8a`, `android-armeabi-v7a`, `android-x86_64` | Android, ABI из `updateAbi` |
| `linux-x64` | Ubuntu/Debian x64 (DEB) |
| `windows-x64` | Windows x64 (ZIP) |
| `ios` | iOS (пакета нет — открывается страница релиза) |

## Выпуск манифеста

Генератор: `tools/release/update-manifest.py`. Он берёт версию и сборку из
`app/lib/version.dart`, сверяет их с `app/pubspec.yaml`, считает размер и SHA-256 пакетов,
собирает payload, подписывает его ключом проекта, **проверяет открытую часть ключа по
закреплённому `update-ed25519.pub`** и перечитывает записанный файл, прогоняя по нему те же
правила, что и клиент. Манифест, который приложение отвергло бы, записан не будет.

```bash
# 1. Проверить, что версия в version.dart/pubspec.yaml — та, что собрана.
#    Для 0.24.2 это 0.24.2+5019.

# 2. Подписать манифест по готовым пакетам (ключ — вне репозитория).
python3 tools/release/update-manifest.py \
  --key ~/.keys/update-ed25519.key \
  --asset android-arm64-v8a=releases/XIO-Full-0.24.2-android-arm64-v8a.apk \
  --asset android-armeabi-v7a=releases/XIO-Full-0.24.2-android-armeabi-v7a.apk \
  --asset linux-x64=releases/XIO-0.24.2-ubuntu-amd64.deb \
  --notes "XIO 0.24.2 — каскад двух серверов, тише батарея, −7 МиБ APK." \
  --assume-installed-build 5018 \
  --out releases/XIO-update.json

# 3. Приложить манифест к тому же релизу (publish.ps1 грузит всё из каталога).
pwsh -NoProfile -File tools/release/publish.ps1 \
  -Tag v0.24.2 -AssetsDir releases -NotesFile docs/release-notes-0.24.2.md

# 4. Проверить уже опубликованное: подпись, правила клиента и совпадение файлов.
python3 tools/release/update-manifest.py --check releases/XIO-update.json \
  --asset-dir /path/to/downloaded/assets

# 5. Убедиться, что ассет виден в ленте так, как его ищет приложение.
curl -s "https://api.github.com/repos/rukazax/xio_vpn/releases?per_page=30" \
  | python3 -c 'import json,sys
for r in json.load(sys.stdin):
    if r["tag_name"].startswith("v") and not r["draft"]:
        print(r["tag_name"], [a["name"] for a in r["assets"] if a["name"]=="XIO-update.json"])'
```

Альтернатива для точечной загрузки одного файла и для проверки после публикации:

```bash
curl -sS -X POST \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @releases/XIO-update.json \
  "https://uploads.github.com/repos/rukazax/xio_vpn/releases/433728341/assets?name=XIO-update.json"
```

Порядок важен: сначала собираются **окончательные** пакеты, потом подписывается манифест.
Любое изменение байтов APK/DEB после подписи делает `sha256` неверным, и установка
прервётся на проверке контрольной суммы.

### Ключ подписи

Закрытый ключ в репозиторий не входит (`releases/`, `.signing/` и архивы его не содержат).
Формат — 32 сырых байта Ed25519. Открытая часть должна совпадать с
`app/assets/security/update-ed25519.pub`; генератор отказывается подписывать чужим ключом.

Для форка: создайте свою пару, замените `update-ed25519.pub`, **пересоберите и
распространите приложение**, и только затем публикуйте манифесты своим ключом. Ротация
ключа возможна только вместе с обновлением приложения: старые сборки доверяют только
закреплённому ключу.

## Что видит пользователь, если манифеста нет

Приложение просматривает ленту релизов и для каждого тега новее установленного требует
ровно один ассет с именем `XIO-update.json`. Если ассета нет (как было в 0.23.0–0.24.2 до
этой правки), релиз **молча пропускается**: ни ошибки, ни диалога, ни записи в журнал.
Недельная проверка продолжает идти, ручная кнопка «Проверить обновления» отвечает
«Установлена последняя версия» — то есть отсутствие манифеста неотличимо от отсутствия
новых версий. Именно поэтому канал умирает незаметно.

Если манифест есть, но неверен (подпись, тег, сборка, размер, SHA-256), поведение такое же:
релиз отбрасывается, пользователь не получает ни обновления, ни объяснения.

## Ограничения текущей схемы

1. **Один `build` на все платформы.** Манифест описывает одну сборку, а пакеты могут быть
   собраны в разное время. Нельзя публиковать `build` 5019, если для платформы лежит пакет
   предыдущей сборки: клиент скачает его, установит и снова увидит «новую» сборку. Поэтому
   в манифесте 0.24.2 нет `windows-x64`: единственный ZIP на релизе — `XIO-Full-0.24.1`
   (Windows в 0.24.2 не пересобирался). Для Windows клиент открывает страницу релиза.
2. **Один пакет на ABI.** Канал не различает сборки Client и Full: в манифест попадает один
   APK на архитектуру (сейчас — Full). Пользователь Client-сборки получит Full с серверной
   частью. Если нужно наоборот, передайте в `--asset` путь к `XIO-Client-…apk`.
3. **Нет постепенного раскатывания.** Манифест один на релиз: либо обновление видят все, либо
   никто. Отозвать его можно только удалением ассета (следующая проверка просто не найдёт
   обновления).
4. **Симметричная подпись (HMAC) непригодна.** Клиент умеет проверять только Ed25519
   закреплённым открытым ключом; HMAC-манифест он не примет ни при каком секрете. Секрет в
   переменной окружения был бы не слабее и не проще, а просто неработоспособен.
5. **Приватность.** Проверка — обычный HTTPS-запрос к GitHub, который видит IP-адрес; профили
   и учётные данные не передаются. Подпись защищает от подмены файлов и от чужого релиза, но
   не от компрометации ключа выпуска или самого устройства.
